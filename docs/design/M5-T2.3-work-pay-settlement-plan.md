# M5-T2.3 — Actual work pay settlement — proposed plan

**Status: APPROVED by Codex on 2026-10-20 — implementation approved; assumptions below preserved unchanged.**
This is a Codex-delegated working proposal for gate T2.3, **not a direct user instruction** and **not a balance approval**. The authoritative contract is [IMPLEMENTATION_PLAN](../IMPLEMENTATION_PLAN.md) §3.1 and problems P6.2/P7.1–P7.3 in [TECHNICAL_PROBLEMS](../TECHNICAL_PROBLEMS.md); method in [DEVELOPER_GUIDE](../DEVELOPER_GUIDE.md) §4.5/§4.6. Prior accepted gates: T2.1 attendance ([plan](M5-T2.1-work-attendance-plan.md)), T2.2 settlement bookkeeping ([plan](M5-T2.2-work-settlement-plan.md)).

## Scope decision: pay, not output

The gate names P6.2/P7.2. P6.2 (effort → output) requires a **recipe, tools and real resources**; its check is "attention without tools must not create full output". No recipe, tool, worksite or Establishment exists in the codebase yet, so producing goods in this slice would fabricate output from a promise — exactly what P7.2 forbids ("a promise does not become product"). T2.3 therefore delivers the **pay half of P7.2** plus the **P7.3 idempotence property** for the work wage, and defers production/output to a later Establishment/worksite slice.

## Problem with the current baseline

`Realm::day_payroll` (`core/src/realm.cpp`) builds a flat work wage gated on `EmploymentManager::has_active_work(p, day_)` and a separate periodic role top-up:

- teacher (`p.job_kind == 1`) → public claim `2`; any other active worker → private claim `1 + skill/25`; both charged to province `p.region`.
- periodic non-Civilian **role top-up** `20` every 30 days via the `!p.hired_by && day_%30==0 && family!=Civilian` branch: Governance → public claim, Economic → private claim. This is a role top-up, **not appointed-office salary**; its amount, eligibility, cadence and routing are **unchanged** in this slice (only the timeline-contract payment mechanism moves into the batch).

The actual **appointed-office salary** is separate: in `Realm::day_people`, `p.hired_by && p.salary_due <= day_` transfers `EmploymentManager::kOfficeSalary` from the employer region's province treasury to the appointee, then resets `salary_due`; if the treasury is short it ends the office instead. Its logic is **unchanged** and it stays outside `day_payroll` and this batch. However, under `timeline_contract == true`, teacher wages and role top-ups can draw on the same province public treasury earlier in `day_payroll`; the treasury available to this later salary—and therefore whether it succeeds or ends the office—can change. This is an **expected shared-account effect**, to be tested and reported; the salary outcome is not claimed to remain identical. Under `timeline_contract == false` the legacy payroll path is exact and this effect does not occur.

The flat work wage pays for an **active assignment**, not for attended work, and ignores physical work location. P7.2 requires pay to follow completed work from a real account.

## Resolved decisions for this plan

1. **Wage:** exactly **1 cash per completed 16 ticks** of physical work attendance, per actor and physical work region. This is a Codex-delegated working assumption, not approved balance.
2. **Replacement:** when `timeline_contract == true`, attendance pay **replaces only the flat assignment-only worker wage**. The periodic non-Civilian role top-up keeps the same eligibility, 20-cash claim amount, 30-day cadence, Governance-public/Economic-private routing and relative order among role top-ups; it is included in the batch as a **non-wage** claim and never advances a work-pay watermark. Its **cash effect is not guaranteed byte-identical** under `timeline_contract == true`: when a work-wage claim shares an underfunded group, the shared `FinanceManager` pro-rata allocation can reduce the top-up's paid share. That is an expected consequence of the new wage policy, not a change to the top-up's amount, eligibility, routing or order. The separate appointed-office salary in `day_people` keeps its exact logic, eligibility, amount, ordering and office-ending behavior, but its available treasury—and therefore whether it succeeds—can change under `timeline_contract == true` because earlier payroll may consume the same public account (an expected shared-account effect tested and reported); under `timeline_contract == false` it is exact. When `timeline_contract == false`, legacy payroll is preserved **exactly** (same claims, routing, ordering, shortage behavior and role top-up; the separate appointed-office salary is also untouched); no regional attendance or pay watermark is read or written.
3. **Region key:** attendance and the paid watermark are keyed by **actor + physical work region**. Money never uses T2.2's actor-only `settled_work_units`; that counter remains bookkeeping only. An actor's remainders and pending pay do not transfer between regions.
4. **Shortage:** underfunding is a successful pro-rata payment, not a reject. Pending wages remain owed while the actor is alive. On death, the unpaid gap is frozen/forfeited for T2.3: it is never paid, transferred to an estate, or turned into a debt record. This is a temporary rule; estate/arrears law is out of scope.
5. **Timing:** payroll stays before settlement. Work is paid at the **next day's payroll**, so the first pay is delayed by one day. There is no retro-pay at adoption or migration.
6. **Atomicity:** every private/public plan, simulated account/treasury/tax state, and claim-to-actor/region allocation is staged before any live write. Any prepare/validate/allocation failure leaves live state untouched.
7. **Migration:** v9/v8/v7 saves migrate to v10 with the legacy global `work_present_ticks` counter preserved **exactly**, and with empty regional attendance and paid watermarks. The preserved global ticks are un-attributed legacy attendance and are never used for pay; prior attendance/settlement does **not** create retroactive pay. Under `timeline_contract == true`, new attendance after migration increments the preserved global counter and the regional counter by the same credit.
8. **Scope:** pay-only; Production/output, recipes, tools, worksites and Establishment remain deferred.

## Data model

`ScheduleBook` (`core/include/polyec/schedule.hpp`) gains two sparse maps keyed by `(actor_id, physical_region)`. Realm has `regions_ + 1` valid province IDs, numbered `0` through `regions_` inclusive; a region key is valid iff `0 <= region <= regions_`. Actor IDs may repeat across regions: only `(actor, region)` pairs are unique, so the same actor appearing under several regions is valid and must not be rejected.

- `work_present_ticks_by_region` — cumulative post-migration physical work ticks attributed to that region. Positive-only, and only when `timeline_contract == true`. Updated from the same per-tick presence predicate as T2.1: `alive ∧ destination == -1 ∧ person.region == session.region`, with at least one matching typed `Work` session. Overlapping sessions in the same region count once per tick. Every new tick credited to the global `work_present_ticks` counter is also credited to exactly one of that actor's regional keys (see invariant). This map does **not** partition legacy global ticks: a migrated v9/v8/v7 save preserves its global counter exactly while the regional maps start empty, leaving a non-negative un-attributed gap that is never attributed and never used for pay. It is a **pay-attendance** counter, not a copy of T2.2 `settled_work_units`.
- `paid_work_units_by_region` — cumulative completed 16-tick blocks already paid in that region. Positive-only, monotonic, never above the regional eligible units.

The unique `(actor, region)` key count in each map is bounded by `people_.size() * (regions_ + 1)` — one key per actor per inclusive region slot, since exactly `regions_ + 1` province IDs are valid. Compute this bound with checked/size-safe arithmetic and reject on multiplication overflow; the loader must enforce `count <= bound`. Key validity applies independently to both maps.

New constants:

- `kAttendanceTicksPerWorkUnit = 16` (existing work-unit size; no change to T2.2 semantics).
- `kWorkWagePerUnit = 1` cash per completed unit. This is a working assumption, not a balance approval.

T2.2's `settled_day` and `settled_work_units` remain unchanged and are **not read by payroll**.

## Pay formula

For alive actor $$a$$ and physical work region $$r$$:

$$
T_{a,r} = \text{work\_present\_ticks\_by\_region}[(a,r)],
\qquad
E_{a,r} = \left\lfloor \frac{T_{a,r}}{16} \right\rfloor,
\qquad
P_{a,r} = \text{paid\_work\_units\_by\_region}[(a,r)].
$$

The due units and cash claim are:

$$
D_{a,r} = \max(0, E_{a,r} - P_{a,r}),
\qquad
\text{claim}_{a,r} = D_{a,r} \times 1.
$$

Only claims with $$D_{a,r} > 0$$ are emitted. The work-pay watermark advances by **gross wage units actually paid** (before tax withholding), not by net cash, by a non-wage role top-up, or by the separate appointed-office salary. With a wage of 1 per unit, gross paid cash equals the number of units advanced.

Each region has its own remainder. For example, 8 ticks in region A plus 8 in region B pays 0, and 15 in A plus 15 in B pays 0; neither remainder transfers.

## Timing: payroll before settlement means a one-day delay

`day_payroll` remains the first phase and `day_settlement` remains at the completed day boundary. Work performed during day $$D$$ is therefore not paid by that day's payroll; it becomes payable at the next day's payroll. The first complete block earned on day $$D$$ is paid on day $$D+1$$. T2.3 does not move either phase and does not create a catch-up payment.

This is intentional: the plan does not use T2.2's end-of-day settled units for money, and it does not claim that a newly adopted or migrated v9 save has a payable balance.

## Payroll algorithm under `timeline_contract == true`

1. Build periodic non-Civilian role-top-up claims exactly as the legacy `day_payroll` branch does (`!p.hired_by && day_%30==0 && family!=Civilian`), tagging each as the non-wage claim `role_topup(actor, family)`. Keep the legacy 20-cash amount, 30-day cadence, Governance-public/Economic-private routing and relative order among role-top-up claims. They are never included in `paid_work_units_by_region`.
2. For every alive actor and every positive regional attendance key, compute $$D_{a,r}$$. Skip dead actors (their pending gap is frozen/forfeited). Emit each positive claim as `work_wage(actor, region)`.
3. Route wage claims using the same public/private predicate as the legacy worker wage: teacher work → public account of the physical work region; other work → private employer of the physical work region. Route role-top-up claims to the same public/private group as the legacy branch does today. The separate appointed-office salary is not built, routed or tagged here; `day_people` continues to pay it with unchanged logic outside this batch, though shared-treasury availability can change its later success under timeline contract.
4. Group claims by `(region, public)` in deterministic order: **regions ascending, and within each region private before public**, matching the existing `Realm::day_payroll` loop. Within a group, order claims by **actor ID ascending**; if the same actor has both, emit `work_wage(actor, region)` **before** `role_topup(actor, family)`. This fixed order makes rotation/tie results reproducible and preserves the role top-up's relative actor order. Build explicit allocation metadata mapping every claim index to either `work_wage(actor, region)` or non-wage `role_topup(actor, family)`; never infer an allocation from claim order after money moves. Do not iterate an unordered map to build the batch.
5. Stage the batch described below. Underfunding is not a failure.
6. After a successful batch commit, advance each work-pay watermark by the batch's gross paid amount for that `work_wage` claim only. `role_topup` claims and the separate appointed-office salary never advance a work-pay watermark.
7. Do not emit, pay, or accrue anything from T2.2 `settled_work_units`. Do not add a claim for an actor with $$D_{a,r} == 0$$.

### Staged all-or-nothing commit

`FinanceManager` gains an opaque batch staging path (for example `PayrollBatchPlan` with `prepare_batch`/`apply_batch` in the existing header) or an equivalent internal batch transaction. It must provide the following contract:

- `prepare_batch` receives all ordered `(region, public)` groups and their claims. It creates a staged overlay initialized from the live read-set of every affected account cash/tax, province treasury/tax/receipt counter and any shared state. It runs the existing allocation logic group by group **against the overlay**, applying each staged group to the overlay before preparing the next. Thus shared treasury/tax is simulated exactly once, and later groups cannot overspend money already promised to earlier groups.
- The batch plan records every sub-plan, the gross paid amount for each claim, the final staged money deltas, and the allocation tags needed by `Realm` to advance regional watermarks only for `work_wage` claims and never for non-wage `role_topup` claims.
- Under `timeline_contract == true`, role-top-up claims are staged in the same batch but tagged non-wage. Their legacy eligibility, 20-cash amount, 30-day cadence, routing and relative order are preserved; only their payment mechanism moves into the overlay/batch. **Their paid share is not guaranteed identical:** the batch uses the same ordered groups and shared pro-rata allocation, so a work-wage claim added to an underfunded group can reduce the top-up's paid share even though its claim amount, eligibility, routing and order are unchanged. A role-top-up staging failure aborts the whole batch before any live write.
- Before commit, `Realm` also builds the complete next versions of `work_present_ticks_by_region` and `paid_work_units_by_region`, validates all keys, bounds and invariants, and reserves all storage.
- No live `Person`, `Province`, treasury, tax, receipt or `ScheduleBook` field is written during preparation. If any claim build, prepare, validation, allocation or map update fails, the live state remains bit-identical.
- The live commit is a single prevalidated batch: write all precomputed money deltas, then swap the fully built schedule maps. `apply_batch` must validate the day and complete read-set before its first write and then perform only non-throwing scalar writes/container swaps; no validation that can throw may run after a live write.
- The legacy `timeline_contract == false` path is not reimplemented through this batch. It keeps its existing code path and behavior exactly.

## Shortage, death and idempotence

- `FinanceManager` pays pro-rata when the real account cannot cover the group. A unit is never created from nothing and total money is conserved.
- The watermark advances only by gross paid units. Unpaid `D_{a,r}` stays pending implicitly as $$E_{a,r} - P_{a,r}$$ and can be paid on a later day while the actor is alive and the employer is funded.
- Pending is defined only for alive actors. If an actor dies with an unpaid gap, that gap is frozen and forfeited for T2.3; no further payroll claim is emitted and no estate/debt record is created. Any later estate/arrears feature must define a new rule.
- Idempotence (P7.3): the watermark is monotonic and bounded by regional eligible units. Re-processing the same boundary, reloading a mid-stream save, or splitting an advance cannot pay the same completed block twice.
- Taxes reduce net cash and still flow through the existing accounting; they do not create an unpaid wage gap when the gross due was fully allocated.

## Invariants (`Realm::invariant`)

- `work_present_ticks_by_region` entries: valid actor, valid region in `[0, regions_]` inclusive, value `> 0`, and for every actor the checked sum of that actor's regional ticks is `<=` the global counter: `sum_r work_present_ticks_by_region[(a,r)] <= work_present_ticks[a]`, treating absent `(a,r)` entries as zero and computing the sum with checked arithmetic. This is deliberately an inequality, **not** equality: under `timeline_contract == true`, on fresh v10 data and for every post-migration tick, both counters advance by the same credit and must remain in exact increment parity, while the non-negative difference `work_present_ticks[a] - sum_r ...` is the preserved legacy un-attributed attendance from v9/v8/v7 migration. That gap is never attributed to a region and never used for pay. A regional sum greater than global is invalid.
- `paid_work_units_by_region` entries: valid actor and region (same inclusive `[0, regions_]` range); value `> 0`; key exists in regional attendance; value `<= floor(work_present_ticks_by_region[(a,r)] / 16)`.
- Both maps are empty when `timeline_contract == false`.
- Neither regional map contains more unique `(actor, region)` keys than `people_.size() * (regions_ + 1)`; the bound is computed with checked/size-safe arithmetic, and an overflow or `count > bound` is rejected before allocation.
- T2.2 `settled_day` and `settled_work_units` semantics are unchanged and are not constrained by the pay watermarks.
- Total-money conservation is unchanged (`FinanceManager` + `total_money` invariant already enforce it).
- No actor-region watermark can exceed the regional attendance-derived maximum.

## Save `POLYEC_REALM_10` / `SCHEDULE_4`

- The schedule header adds two record counts: regional work ticks and paid work units. Each count is bounded by `people_.size() * (regions_ + 1)`, computed with checked/size-safe arithmetic; reject an overflowing bound or `count > bound` before allocating or reading records.
- Tick records are `actor region ticks`; paid records are `actor region units`. Both are sorted by ascending `(actor, region)` for deterministic bytes/fingerprints. Zero entries are omitted.
- Load validation: counts within the checked bound above; key validity for **both** maps—each actor ID in range, each region in `[0, regions_]` inclusive (Realm has `regions_ + 1` valid province IDs), and each `(actor, region)` pair unique; actor IDs may repeat across different regions and that is valid; ticks `> 0`; units `> 0`; each paid key must have a matching regional tick record; units `<= floor(ticks/16)`; the per-actor regional tick sum is `<=` global `work_present_ticks` under the invariant above (checked sum; a greater sum is invalid, and the non-negative gap is preserved legacy un-attributed attendance that is never used for pay); both maps empty when `timeline_contract == false`.
- Migration from `POLYEC_REALM_9` / `SCHEDULE_3`: preserve employment type and settlement (`settled_day`, `settled_work_units`) exactly; preserve the legacy global `work_present_ticks` counter **exactly** (do not reset it); initialize both regional maps empty; and re-serialize as v10. The preserved global ticks are un-attributed legacy attendance: no regional attendance is reconstructed from them, and no paid watermark is seeded from `settled_work_units`; therefore there is **no retro-pay**. Under `timeline_contract == true`, new attendance after migration increments the preserved global counter and the regional counter by the same credit, producing exact increment parity from that point on.
- `POLYEC_REALM_8` / `SCHEDULE_2` and `POLYEC_REALM_7` / `SCHEDULE_1` keep their existing migration paths, preserve any legacy global attendance counter exactly, also initialize the regional maps empty (no retro-pay, no reconstructed attribution), and then re-serialize as v10 under the same rule.
- A mid-day v10 save preserves partial regional ticks, the global attendance counter and the paid watermark. Restore continues without re-crediting prior blocks; the next payroll sees only the saved cumulative attendance, and under `timeline_contract == true` new ticks continue to increment both counters by the same credit.
