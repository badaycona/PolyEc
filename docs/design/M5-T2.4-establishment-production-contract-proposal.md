# M5-T2.4 — Establishment and production contract proposal

**Status: implementation direction delegated by the user on 2026-10-20; Gates 1–6b1 have implementation evidence.** The main Codex tab owns planning, implementation, and review under the user's 2026-10-20 execution experiment; each production slice keeps its own bounded plan and gate. The delegated assumptions below are working rules, not calibrated balance, and must stay labeled as such in code/docs.

## Basis and current limits

- `docs/CURRENT_TASK.md`: T2.1 work attendance, T2.2 work-unit bookkeeping and T2.3 wage settlement are accepted. All defer actual production, Establishment identity and worksite attribution.
- `docs/IMPLEMENTATION_PLAN.md` §2, §3.1, §4 and §15.1–15.3: an establishment has an owner, workplace, capacity, labor, inputs, assets and wear; the economic catalog has 16 groups; production is limited by labor, inputs, resources and season. Work attendance is physical presence, and T2.2's 16 ticks/unit and T2.3's 1 cash/unit are working assumptions.
- Current core is only a pilot: `Province` owns one aggregate `firm` account and seven stock/price slots; `Person` and `ScheduleCommand` identify Work by region; pay and attendance maps are keyed by actor and region. There is no Establishment class, canonical 16-good type or recipe catalog. Realm does have 28 tracked organization balances (`organization_funds_`), though organization membership/IDs are a fixed pilot schema rather than full organization entities. Any implementation must explicitly migrate/bridge these fields; it cannot treat the pilot firm as an establishment.

## Proposed contract decisions

| Decision | Proposed rule for review | Status / consequence |
|---|---|---|
| Establishment identity and lifetime | Realm owns sparse `Establishment` records keyed by stable `uint64` IDs allocated from `next_id_`. Each has an operating region, owner reference, an explicit industry ID, capacity, cash account and inventory. Other records refer by typed ID; no per-establishment scene node or model. Initial owner kinds are a living Person, a public Province authority, or an existing organization account ID in `1..28`. A creator may fund a Person-owned establishment only for themselves; an organization-owned one only when they are a member and the establishment is in the account's home region `floor((org_id-1)/4)`; a public one only as Governance + taxing authority + charter for the same Province. The 28 existing organization accounts are tracked balances; do not replace or duplicate them. | **Delegated working rule.** Organization IDs remain the current fixed account IDs; do not imply they are full organization entities with governance/lifecycle. Starter industry IDs: 1 cloth workshop, 2 tool workshop, 3 military-supplies workshop. |
| Worksite attribution | A typed Work session names an establishment ID; its region is derived from that establishment and must match the actor's physical region for attendance. Generic sessions remain unchanged. Overlapping Work sessions at the same establishment continue to count physical ticks once. Reject a submit that overlaps a Work session at a different establishment, so one actor cannot produce labor at two sites during the same tick. | **Delegated gameplay rule.** Requires extending the command/save/binding path and changes reject behavior for cross-site overlaps. |
| ID namespace | Establishment IDs use the Realm non-Person entity counter `next_id_`, shared with Loan/Project/Investigation/Proposal IDs. Person IDs are a separate positional namespace (`people_[i].id == i+1`) and may have the same numeric value without referring to the same entity. Check uniqueness across the shared non-Person domain; do not change dense Person IDs or birth allocation to `next_id_`. | Prevents an invalid cross-type collision rule from breaking Person indexing. |
| Work-unit conversion | Reuse the accepted T2.2 definition: 16 eligible unique Work ticks produce one cumulative unit. **Proposed assumption:** one new unit attributed to an establishment funds at most one recipe batch, independent of role/skill for this first settlement. Do not award historical or unassigned units to a newly selected site. | 16 ticks is an existing working assumption; one batch/unit is new and provisional. |
| Recipes | Use integer batch recipes over the 27 canonical `GoodId` products under 16 `GoodGroup`s; each recipe explicitly lists input quantities and output quantities. Starter recipes: 1 Fiber → 1 Cloth; 1 Iron + 1 Fuel → 1 Tools; 1 Tools + 1 Cloth → 1 MilitarySupply. No implied substitution between groups or variants. Additional goods receive explicit source/recipe/market rows as M5 slices proceed. | **Delegated working rules**, not sourced balance. One output unit per listed input unit is a first-pass assumption; acceptance requires complete, reviewed production coverage for the M5 catalog, including variant constraints. |
| Resource and season factors | For the initial recipe slice, do not claim to simulate agriculture or natural-resource extraction. Crafted recipes have no implicit resource or season multiplier; capacity is an explicit integer maximum of batches per day. Add resource/season-dependent recipes only with their own state and rules. | Explicitly defers the `rho_resource` and `mu_season` portions of §15.3 for the crafted-recipe slice. This does not satisfy all of §15.3. |
| Input shortage | At a completed day boundary, process no more than `min(new eligible work units, capacity remaining, floor(each available input / recipe input))`. Consume all inputs and create all outputs for those complete batches in one staged transaction. Advance the work-unit watermark by the units considered, including units for which inputs were short; missed production does not accrue labor debt or replay later. Reject/overflow leaves inventory and watermarks unchanged. | **Delegated working rule:** shortage loses that day's unused production opportunity. Prevents a later restock from producing without new labor. |
| Cash, stock and wages | Establishment cash and inventory are separately owned assets, distinct from Province treasury/stock and Person inventory. Establishment-funded payroll claims draw from its cash account; public work draws from the relevant public account. Existing T2.3 one-cash/unit and retry/forfeit rules remain. Transfers into/out of an establishment must be explicit and conserve value. Do not copy an aggregate balance into a new establishment. | **Delegated accounting boundary.** Gate 1 creates with at least 1 cash; later account-transfer/payroll slices must conserve all tracked balances, including `organization_funds_`. |
| Day order and idempotence | Realm remains sole world owner. A pure production planner stages all establishments in stable ID order after daily attendance is finalized; apply commits stock, cash and per-establishment/actor processed-unit watermarks once. If the day operation is replayed or retried, no second output is created. Keep existing phase order unless a reviewed diff demonstrates the exact new phase point. | Follows R3/R1 ownership and staged-write patterns; the production phase point needs a plan against the live pipeline. |
| Commands, view and learned policy | All establishment creation, work assignment, funding and transfers use Realm commands with validate-before-mutate semantics. The player and AI use the same command path. Before autonomous policy can select a worksite, provide authorized establishment IDs and relevant state in observations/action masks; no hardcoded site choice or hidden strategy. | Observation/action/model changes are likely. Their schema and compatibility require a separately reviewed bounded plan; this proposal does not authorize them. |
| Save and migration | Add a versioned establishment section and bump the Realm save schema. Establishment inventory uses the 27 canonical `GoodId`s under 16 groups. Before any production recipe or market command can use newly introduced goods, a reviewed catalog-migration slice must expand Person/Province/Campaign holdings and map old slots explicitly: food→DryFood, fiber→Fiber, cloth→Cloth, iron→Iron, fuel→Fuel, tools→Tools, horses→Horse; new products begin at zero. Loading creates no establishments and retroactively assigns no work. New establishments start only through explicit funded commands. New schema load stages entities, validates unique IDs, owner/region/recipe references, nonnegative accounts/stocks and watermark bounds, then atomically commits. | **Delegated migration rule.** Preserve every legacy quantity and provide explicit migration/oracle tests before changing the schema. |

## Required follow-on contracts and acceptance limits

This contract is deliberately not a claim that the whole M5 economy is ready. These gates remain required:

1. OpenCode plan must define bounded creation/funding commands for person-owned, organization-owned and public establishments. Funding moves cash/assets from a validated source atomically; it never mints funds and must be at least 1 cash unit.
2. Gate 3 accepted 27 flattened product IDs in 16 groups and the exact seven-slot legacy mapping. Keep those IDs stable. The reviewed Gate 4 plan classifies all products and implements only the three starter recipes; deferred sources require later resource/market contracts and implementation before M5 completion.
3. Use one recipe batch per new work unit and the no-carryover shortage rule as provisional values. Establishment capacity is an explicit positive integer batches/day; initial conservative default is one batch/day unless the scenario sets another value. Do not call these calibrated economy values.
4. Worksite selection uses typed schedule commands, with cross-site overlap rejection; job-contract/employment assignment remains a separate future class unless the plan demonstrates it is required for M5 source-of-truth.
5. Learned policy must be able to select establishments through valid observations/action masks before M5 autonomous production is complete. This requires its own bounded plan and model compatibility gates.
6. Payroll and legacy migration must conserve all source balances; any legacy unpaid work stays unpaid and old saves do not acquire fabricated establishments or output. Add establishment cash to `total_money()` and append a new establishment-cash aggregate to the end of `balances()` so existing indexes 0..8 retain meaning.
7. A Person must be alive to create/fund a Person-owned establishment. If that Person later dies, the record and account remain valid because Person records persist; estate/inheritance transfer is a later slice. Organization ownership validates ID 1..28 and membership at creation. Public ownership validates local Governance authority and region match. Organization membership and local Governance authority rules must be tested against current Realm permissions.
