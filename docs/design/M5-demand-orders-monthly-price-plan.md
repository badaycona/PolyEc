# M5 market orders, allocation, and monthly prices — implementation plan

**Status:** active implementation plan, based on the working decisions in `docs/IMPLEMENTATION_PLAN.md`, section “Quyết định triển khai thị trường và dữ liệu tuyến — 2026-10-22”. The coefficients below are trial settings, not calibrated balance evidence.

## Goal and boundary

Add finite, funded purchase orders to the existing C++ Realm market. A valid order reserves the buyer’s money; at the next daily market settlement the Realm allocates real regional stock, charges the buyer, transfers tax, and refunds every unused part of the reservation. Existing immediate Buy/Sell commands keep their current behavior. New worlds use the monthly price rule; saves created before this feature keep their historical price rule after migration.

This plan does not add long-term contracts, seller strategy, transport between regions, additional product sources, new policy actions, or a claim that the initial price settings are balanced. The allocator will support the contract-priority round so the later contract feature can submit secured obligations; no existing project or proposal will be relabeled as a contract without a corresponding contract rule.

## Source and data ownership

- `Realm` owns open orders, the aggregate escrow account, the monthly demand and unmet-demand totals for each existing region/product pair, and the last market day/month processed. These are authoritative save data; no process-global cache may affect the result.
- `MarketManager` remains a stateless calculation helper. It validates order terms, calculates checked reservation/settlement/tax values, allocates stock across priority rounds, and computes the fixed-point monthly price update. It does not select an order, owner, or strategy.
- The order command carries actor, sequence, operation (place/cancel), order ID for cancellation, region, exact `GoodId`, quantity, and maximum gross unit price. Placement makes a one-day order due at the next completed game day. It reserves the maximum-price amount from personal cash first and the actor’s household fund second, matching existing personal-spend behavior. A fill consumes those reserved portions in that same order; every unused portion returns to its original account. Auto food orders may instead use the resident’s organization fund only under the existing fallback rule. The order stores the exact source amounts for refund. Ordinary callers cannot select the contract or essential priority.
- A successful placement returns the unique order ID in `RealmResult.session`. Rejected or duplicate commands do not change money, escrow, demand, order records, sequence counters, or fingerprints. Cancellation is allowed only to the owner, before settlement, and refunds each original funding source. A rejected cancellation changes nothing.
- Escrow is an internal money balance included in `Realm::total_money()` and `Realm::invariant()`. Creating an order transfers money into escrow; filling transfers only the charged amount to the local firm, then applies the existing tax accounting; cancellation, price difference, and unfilled quantity return their exact reserved value. This must not create or destroy money.
- When an owner dies before settlement, cancel that owner’s open orders before `EstateManager::prepare_death`: personal cash returns to the decedent and therefore enters the existing estate flow, while household or organization money returns to its original account. No order from a dead owner is filled and no refund is paid twice.
- Existing daily food need remains a biological process, not an AI strategy. If the resident has food in personal inventory, consume it as today. Otherwise, when the existing personal/household or organization funding rule can pay, create one internal essential order for the current day at the existing food price. Resolve the day’s essential and submitted orders in one batch before health/death processing; successful food fills improve nutrition/health and consume one food, while an unfilled or unaffordable need applies today’s existing hunger effect. This is the only automatically generated order in this group.

## Allocation and price rules

- Settle a due order at the region’s current listed price only when that price is no greater than its maximum gross unit price. The new order path charges the listed price; legacy immediate Buy remains `listed + 1`, as already specified. The seller is the regional firm account represented by real stock in `Province.stock`; no stock is created for an order.
- Allocate in three ordered rounds: a future contract obligation secured by goods; engine-created essential orders; ordinary funded orders. Within a round, if available stock is short, allocate `floor(stock × order_quantity / total_round_quantity)` to each order, then assign remaining units by the largest exact fractional remainder and ascending order ID. Continue to the next round with only the stock left. Total fills cannot exceed stock. An ordinary order cannot self-label as essential or contract.
- Each valid order contributes its requested quantity once to that region/product’s monthly demand when processed. Its unfilled part contributes once to unmet demand. Cancellation and invalid/rejected placements contribute neither. At the end of the processing day, any unfilled reservation is refunded and the order closes; no stale order remains available for a second fill. Monthly totals are checked integer quantities.
- At day `30, 60, ...`, after that day’s market settlement and production, use `D = monthly demand`, `U = monthly unmet quantity`, `S = regional stock`, and `T = max(1,D)`. If `D == 0`, price is unchanged. Otherwise compute `q = clamp(U/D + (T-S)/T, -1, 1)`, `r = clamp(0.10*q, -0.10, 0.10)`, and `new_price = clamp(round_half_up(old_price × (1+r)), 1, 1,000,000)`. Implement ratios and rounding with checked integer arithmetic only; do not use floating point or overflow-prone products. Reset D and U only after every product/region price update has succeeded.
- Use a new versioned `GameplayConfig` representation for market-system version, coefficient 0.10, monthly movement limit 0.10, price floor 1, and ceiling 1,000,000. Reject invalid ranges and floor greater than ceiling. New Realm instances use the new market-system version. Existing config files at version 1 parse with documented trial defaults for new worlds. Older Realm saves migrate to market-system version 0 and retain the legacy price update; they do not silently acquire dynamic prices.

## Save, migration, and validation

- Bump the Realm save schema from 25 to 26. Add a versioned market section for escrow, open orders and funding splits, demand/unmet totals, the last settled day and last processed month. Snapshot the complete versioned `GameplayConfig` in the save.
- Schema 26 rejects duplicate/zero order IDs, invalid actor/region/product references, dead owners with live orders, invalid priorities, out-of-range prices/quantities/days, inconsistent funding sums, escrow totals that do not equal open-order liabilities, negative monthly totals, and a month/day marker that could repeat settlement. Reject before replacing the destination Realm.
- Schema 7–25 migration sets market-system version 0, empty orders/escrow/month totals, and an already-processed marker consistent with the loaded day. Existing prices and their daily legacy recalculation remain in force. Config schema version 1 remains readable; config schema version 2 records the market values.
- Save/load must preserve an order saved before settlement and resolve it exactly once after loading. Save/load after a month update must preserve the price and cleared monthly totals and must not update that month again.

## Self-review before implementation

- **Atomic rejection:** every validation, ownership, sequence, funding, and overflow check occurs before the first write. Settlement stages all affected values and verifies funds, stock, firm balance, tax receipt, IDs, and aggregate counters before commit.
- **Money and goods conservation:** escrow is a counted balance; each fill moves buyer escrow to firm, tax moves firm to treasury, and goods move from regional stock to the buyer. Unused escrow returns to its source. No demand statistic is mutated on rejection/cancellation.
- **Order fairness and reproducibility:** each tier is isolated; proportional shares use exact integer quotients/remainders and stable ID tie-breaking. Save data includes every input that can change future allocation.
- **Time and persistence:** only completed game days settle orders. Pause does not settle; partial ticks do not settle; month update is marked once and uses the same stored totals after reload. Old saves remain on the old price rule.
- **Boundary clarity:** the first allocation tier is ready for a later secured-contract producer but has no live producer until the contract feature exists. The group will not call contract gameplay complete. There are no automatic strategic orders; only existing food survival creates essential orders.
- **Potential conflict:** current immediate Buy uses `price+1`, while daily food consumes at `price`. The separate order path uses listed price as its gross unit price; this keeps both current code paths unchanged and makes the limit-price comparison explicit. New tests must lock this difference.
- **Review limit:** this plan is self-reviewed in the primary tab; an independent implementation reviewer is not available in this workspace. The final report will state that limit rather than imply independent review.
