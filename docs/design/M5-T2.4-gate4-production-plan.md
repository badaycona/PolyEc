## Contract correction and scope

Gate 3 defines **16 GoodGroup categories and 27 flattened GoodId products**. The earlier T2.4 proposal's phrase “16 canonical good IDs” is stale; Establishment stock, recipes, ledgers and save records use `GoodId` (27), while group is descriptive metadata. Legacy action/cargo slots remain the seven-item adapter. Do not renumber the accepted IDs or widen the seven-slot action/observation in this gate.

This gate adds a deterministic, staged daily production transaction for the three already-delegated starter industries only. It does not claim all M5 goods are producible. The matrix below assigns every current product a source class and variant rule; rows marked deferred remain unavailable to production until their own resource/market contract and implementation pass. T2.2's 16 ticks/unit, one batch per newly eligible unit, one output per listed input unit, capacity one batch/day by default, and no shortage carryover remain provisional working assumptions, not calibrated balance.

## Before → after and ownership

- Before: `Realm::day_production()` runs a Province-level cloth/tools pilot every 30 days; site attendance is stored in `ScheduleBook::work_present_ticks_by_establishment`; Establishment owns canonical 27-slot inventory and cash; Realm owns ledgers, time, IDs, invariant and save atomicity.
- After: at the existing production phase, Realm asks a stateless production planner to stage eligible Establishments in ascending stable ID order. The planner reads each site's industry, inventory, capacity, actor/site attendance and processed-work watermark; it returns bounded per-site input/output/watermark deltas plus aggregate `produced_`/`consumed_` deltas. Realm validates and commits the complete day's deltas once.
- A site's cumulative eligible units are `floor(site_ticks / 16)`. For each day, consider all units newer than that site's actor watermark. The number of complete batches is `min(new units, capacity, every required input / recipe input)`. Advance the watermark through all living actors' units considered, even when capacity or inputs limit batches; when an actor is dead, advance that actor's watermark to the eligible total with zero output to permanently forfeit the units. Thus unused capacity, death and shortage do not create labor debt or carry over. Output and input quantities are integer, nonnegative GoodId counts.
- Attendance is read only from `work_present_ticks_by_establishment`; do not add actor-global or region attendance a second time. Work overlap at one site is already union-counted; cross-site overlap is rejected by Gate 2.
- Keep Realm as sole state owner and preserve `day_production()` phase position. Do not introduce manager-owned live state, RNG, wall-clock scheduling or policy decisions.
- Establishment creation/funding currently supplies cash only, and no approved goods-transfer or market command exists. The new producer therefore consumes any valid site stock delivered by existing internal/legacy paths; production fixtures must stage canonical inventory through literal save fixtures. Until a later explicit stock-transfer/market gate, a newly created site may have no usable inputs in normal gameplay. Do not mint inputs or silently add a transfer command here.

## Legacy production boundary

Avoid producing Cloth/Tools twice from the same region-level pilot and the new workshops. Preserve the old Province pilot behavior for legacy timeline-off worlds. Under `timeline_contract`, split the legacy output loop and disable Cloth only when that region has a ClothWorkshop; disable Tools only when it has a ToolWorkshop. A ToolWorkshop must not disable Cloth, and a ClothWorkshop must not disable Tools. Regions without the matching industry retain their current pilot recipe. Preserve the existing monthly unrest update regardless of whether either recipe is enabled. The new site recipe consumes only Establishment stock and records its input/output deltas in Realm conservation ledgers. Do not change the separate daily non-employed person output or quarterly harvest in this gate.

This compatibility switch is intentionally local to `(region, industry)` and derived from authoritative Establishment records; no duplicate mode flag is added. Tests must prove empty-site legacy replay remains unchanged and adding a site does not duplicate its matching legacy recipe.

## Save, conservation and transaction rules

- Store sparse per-actor processed-work-unit watermarks and `last_production_day` on Establishment. Watermarks are cumulative, positive-only, sorted by actor ID on write, and cannot exceed that actor/site's eligible attendance units. Day is within `[0, Realm::day()]`.
- Add `ESTABLISH_3`, bump Realm schema to `POLYEC_REALM_14`, and continue `SCHEDULE_5` (the live schedule codec already writes this tag for schemas 12–13). Read schema 13 `ESTABLISH_2` and schemas 7–12 with their historical formats. For schemas 12–13, initialize each site's processed watermark to `floor(saved site attendance ticks / 16)` so accumulated pre-Gate-4 work does not produce retroactively. For schemas 7–11, no site-specific attendance exists; initialize watermarks empty. All migrations begin with `last_production_day = loaded Realm day`. Existing pre-Establishment saves still create no sites.
- Stage all affected stock, watermarks, production-day fields and global goods ledgers before any production-owned live write. A malformed industry, invalid actor key, inconsistent attendance/watermark, negative quantity, capacity violation or checked-arithmetic overflow rejects the production transition without partially changing sites or goods ledgers. `day_production()` runs inside the already-advancing Realm day pipeline, so this slice does not promise rollback of earlier day phases or the day/cursor; it must not write RNG or facts. Planner output is not caller supplied.
- Batch arithmetic is checked before division/multiplication/addition. The output stock, input stock, `produced_`, `consumed_` and all watermarks are validated together. On commit, all map/vector allocations must already have succeeded; commit operations must be nonthrowing swaps/scalar writes or use a rollback plan.
- The invariant remains `closing held + consumed == opening + produced` for each GoodId, counting Person, Province, Establishment and Campaign-bonded goods. For each craft batch, subtract exact inputs from the owning Establishment, add exact outputs to the same Establishment, and increment the Realm ledgers by matching quantities.
- Re-running the production phase for an already processed day must have no second output. A repeated day is a no-op/reject before mutation. Production does not touch establishment cash or payroll; employer-funded wages/transfers are a separate reviewed gate.
