## Scope and semantics

T2.2 turns the cumulative unique attendance counter from T2.1 into a **bookkeeping unit counter at completed day boundaries**. It is not economic settlement: it does not produce goods, pay wages, allocate work, or change any person, cash, province, stock, payroll or RNG state.

- The settlement factor is $$T = 16$$ attendance ticks per cumulative unit. This factor is a **Codex-delegated working assumption, not direct user instruction and not balance approval**.
- The game day is 64 attendance ticks, so maximum full attendance yields $$64/16 = 4$$ units per day.
- Settlement runs once at each completed day boundary, after the other daily phases, from the persistent cumulative counter `ScheduleBook::work_present_ticks`.
- For actor $$a$$, the cumulative eligible unit count is $$u_a = \lfloor \text{ticks}_a / T \rfloor$$ where $$\text{ticks}_a$$ is the lifetime unique physical Work attendance.
- Because the division is recomputed from the cumulative counter, the remainder ticks are carried implicitly across days. There is no remainder field and no reset.
- Settlement never double counts: a value is written only when the newly eligible count is greater than the previously settled count for that actor.
- The completed-day watermark is $$\text{settled\_day} = \lfloor \text{cursor}/64 \rfloor$$.
- Units are **bookkeeping only**. They are not effort, delivered attention, output, production, pay, wage, wealth or a claim on resources.

## Data model

`ScheduleBook` (`core/include/polyec/schedule.hpp`) gains:

- `int64_t settled_day = 0` — highest completed day that has been settled.
- `std::unordered_map<uint64_t,int64_t> settled_work_units` — actor → cumulative settled units, sparse and positive-only.

`Realm::day_settlement()` (`core/src/realm.cpp`) is declared in `core/include/polyec/realm.hpp` and invoked as the final phase of `RealmDayPipeline::run`, after `day_end()`. It:

1. Does nothing when `timeline_contract == false` or when no day has completed.
2. Computes `eligible = work_present_ticks[actor] / 16` for each valid actor with attendance.
3. Raises the stored unit value only when `eligible` exceeds the prior value.
4. Sets `settled_day = cursor / 64`.

The phase is pure schedule bookkeeping: it must not mutate attendance, sessions, people, provinces, cash, facts, RNG, production or payroll.

## Serialization and migration

- Save is `POLYEC_REALM_9` / `SCHEDULE_3`.
- The schedule header adds `settled_day` and a settled-entry count. Settlement records are serialized by **ascending actor ID** for deterministic bytes and fingerprints, matching attendance serialization.
- On load, a zero unit value is normalized away; only positive entries remain.
- Load validation: settled count ≤ `people_.size()`; actor IDs unique and in range; `settled_day ∈ [0, floor(cursor/64)]`; units ≤ `floor(cursor/16)`; units ≤ `floor(attendance/16)` for that actor; non-empty settlement requires `settled_day > 0`; settlement and attendance must be empty when `timeline_contract == false`.
- `POLYEC_REALM_8` / `SCHEDULE_2` migration preserves typed sessions and attendance, starts settlement empty (`settled_day = 0`), and re-serializes as v9.
- `POLYEC_REALM_7` / `SCHEDULE_1` migration defaults sessions to `Generic` / `region = -1` and starts both attendance and settlement empty, then re-serializes as v9.
- Mid-day save/restore resumes with the same watermark and counters; settlement continues only at the next completed boundary without re-crediting prior attendance.

## Python binding

`bindings/python/realm_binding.cpp` exposes read-only `settled_day` and `settled_work_units(actor)`. There is no writer; all mutation stays behind the Realm command/day path.

## Invariants

- `settled_day` is in `[0, floor(cursor/64)]`.
- Settlement entries exist only when `timeline_contract == true`.
- Actor IDs are valid and unique; unit values are positive after normalization.
- Settled units never exceed the floor of cumulative attendance or the cursor.
- `work_present_ticks` remains the unique cumulative attendance source; settlement reads it without changing it.
- Serialization is deterministic and independent of `unordered_map` iteration order.
