# M5-T2.4 Gate 1 — Establishment identity and funded creation

**Status: accepted by Codex on 2026-10-20; implementation pending.** The user delegated the remaining M5 choices to Codex. Gate 1 implements the Realm-owned Establishment record, funded create command, accounting/invariants and versioned save migration. Production, worksite attribution, market changes and policy/UI wiring remain separate gates.

## Contract and before → after

Realm currently has no Establishment record. `Province::firm` is an aggregate pilot account. Work attendance/pay maps are keyed by actor/region. Saves write `POLYEC_REALM_10` and end in `SCHEDULE_4`.

After this gate, Realm owns sorted Establishments with stable IDs from `next_id_`, region, owner, industry, daily capacity, cash and a 16-slot inventory. A create command transfers at least 1 cash from an authorized existing source. Rejects are atomic. `total_money()` includes establishment cash; `balances()` appends its aggregate at slot 9 while retaining slots 0–8. Save schema becomes `POLYEC_REALM_11` with `ESTABLISH_1` after `SCHEDULE_4`; schema 7–10 loads unchanged and creates no Establishments.

Person IDs stay in their typed positional namespace (`id == index + 1`); they may numerically equal another record ID. Establishment IDs share `next_id_` with Loan, Project, Investigation and Proposal IDs and must be unique within that domain. No Person/birth allocator change.

## Domain and command

Files: `core/include/polyec/establishment.hpp` (new), `core/include/polyec/realm.hpp`, `core/src/realm.cpp`.

- Use strongly typed `EstablishmentOwnerKind { Person=0, Public=1, Organization=2 }` and `EstablishmentIndustry { ClothWorkshop=1, ToolWorkshop=2, MilitarySupplyWorkshop=3 }`. Keep wire values explicit and stable.
- Record fields: `id`, `region`, typed owner kind + owner ID, typed industry, positive `capacity` (initial default 1 batch/day; upper bound 1,000,000), nonnegative `cash`, zero-initialized `std::array<int64_t,16> stock`.
- Create by Realm command with actor and sequence. Person owner must be the living actor; funding comes from their cash. Public owner is the operating Province; creator must be local Governance, `taxing_authority`, and the Province must have `charter`; funding comes from that Province treasury. Organization owner ID must be `1..28`, match actor membership, operate in its home region `(id-1)/4`, and draw from `organization_funds_[id-1]`. Do not duplicate any source balance.
- Initial funding is at least one cash unit. New ID allocation and all writes occur only after validation. Record creation emits Realm fact kind 203; it is unused in current code. Reject does not change fingerprint, actor counters, balances, `next_id_`, facts, or Establishment list.
- A Person dying after creation does not invalidate the record. Person records persist; estate/ownership transfer is outside Gate 1.

## Save, migration and invariants

Files: `core/include/polyec/establishment_section_codec.hpp` (new), `core/src/realm.cpp`, `core/tests/test_realm.cpp`, plus `core/include/polyec/schedule_section_codec.hpp` to keep the existing `SCHEDULE_4` grammar readable under Realm schema 11. Test-only schema expectation updates are in `core/tests/test_schedule.cpp`, `core/tests/test_campaign.cpp`, and `ai/tests/realm_clock_binding_checks.py`.

- Stateless codec writes trailing ` ESTABLISH_1 <count> ... ` with records in strict ID order. Each record stores ID, region, owner kind/ID, industry, capacity, cash and 16 stock values. Empty section is exactly ` ESTABLISH_1 0 `. Reader stages locally, validates encoded integer ranges before enum conversion, and only publishes after complete parse. Realm retains wrapper dispatch, final cross-domain invariants and atomic commit.
- Writer emits `POLYEC_REALM_11`. Schemas 7–10 follow their existing read paths and migrate to an empty Establishment vector; no retroactive site assignment or output. Campaign keeps its quoted Realm boundary and 622-byte Campaign payload unchanged.
- The canonical 16-slot Establishment stock maps legacy goods through `[0,7,8,5,4,10,9]` for old slots `[food,fiber,cloth,iron,fuel,tools,horses]`. Those mapped values join the current seven-slot conservation ledger. New goods without a legacy slot must remain zero. Expanding Person/Province/Campaign holdings to all 16 groups is a required later gate before production or market commands use those groups.
- Invariant checks: sorted unique Establishment IDs; no collision among the shared `next_id_` record types; ID nonzero and below `next_id_`; valid region, typed owner and industry, owner reference/account, capacity range, nonnegative cash/stock, mapped stock conservation, and zero for unmapped goods. Person namespace is checked only for valid positional IDs, not cross-collisions.
- `balances()` appends Establishment cash in slot 9. Existing consumer `native/realm_benchmark.cpp` iterates `balances().size()`; no hardcoded slot-9 consumer exists in active source. `RealmView`, action/observation/reward/model, Python/Godot APIs and bindings remain unchanged in this gate.
